# Guided Experiments

These exercises are designed around a repeatable loop:

1. predict what will happen;
2. create one controlled condition;
3. observe Kafka, Flink, ClickHouse, and Grafana;
4. verify with a CLI or SQL query;
5. compare your explanation with the supplied answer.

Start the lab once before beginning:

```bash
make credentials
make deploy
```

Every exercise can use live Docker logs directly:

```bash
make logs SERVICE=taskmanager
```

For central log search, run `make up-logs`, open Grafana Explore with the Loki
datasource, and start with this bounded-label LogQL selector:

```logql
{compose_project="kafka-flink-clickhouse-lab-monitoring", service="flink-taskmanager"} | json
```

Keep event IDs, run IDs, and payload text in the line filter or parsed JSON;
they are deliberately not Loki labels.

SQL examples read credentials from the ClickHouse container environment, just
like Make targets. They work with passwords generated by `make credentials`.

## 1. Establish a quiet baseline

### Predict

Before producing anything, decide which values should be zero, absent, or idle.
In particular, predict the Kafka group state before the first completed Flink
checkpoint.

### Run

```bash
make produce-baseline
make observe
```

### Observe

- Kafka Console: keys, all six partitions, and consumer group offsets.
- Flink: job graph, records in/out, and the first completed checkpoint.
- Grafana: pipeline throughput and stage latency.
- ClickHouse: row count, active parts, and the four timestamp columns.

### Verify

```bash
make lag
make latency
docker compose exec -T clickhouse sh -ec '
  clickhouse-client --user "$CLICKHOUSE_USER" --password "$CLICKHOUSE_PASSWORD" \
    --query "$1"' sh 'SELECT * FROM perfmon.telemetry_events ORDER BY clickhouse_ingested_at DESC LIMIT 5 FORMAT Vertical'
```

### Questions

- Why can the Kafka group offset update in steps instead of continuously?
- Which clock contributes most to end-to-end delay?
- Why can a low-rate workload create several ClickHouse parts?

<details>
<summary>Explanation</summary>

Flink tracks source positions as it processes records, snapshots them during
checkpoints, and publishes consumer offsets to Kafka when checkpoints complete. JDBC buffers rows by batch
size or interval, so low-rate data can wait for the interval and create small
parts. The timestamp columns make that wait visible instead of blending it into
event age.

</details>

## Intentional duplicates without a failure

### Predict

One original event plus one intentional duplicate should produce two Kafka
sends with the same `event_id`, different `producer_sequence` values, and one
`injected_duplicate=true` flag. ClickHouse keeps both rows.

### Run

```bash
docker compose --profile tools run --rm producer \
  --rate 100 --count 1000 --seed 7 \
  --duplicate-rate 1 --late-rate 0 --hot-tenant-rate 0 \
  --bad-json-rate 0 --trace-sample-rate 0
```

### Observe and verify

The final producer log should report 1,000 originals and 2,000 acknowledged
sends. In the absence of recovery replays, the run should eventually have 2,000
ClickHouse rows representing 1,000 event IDs. Copy its `producer_run_id`, then
run the following query after replacing `RUN_ID`:

```bash
docker compose exec -T clickhouse sh -ec '
  clickhouse-client --user "$CLICKHOUSE_USER" --password "$CLICKHOUSE_PASSWORD" \
    --param_run_id "$1" --query "
      SELECT event_id, count() AS rows, uniqExact(producer_sequence) AS sends,
             countIf(injected_duplicate) AS intentional_copies
      FROM perfmon.telemetry_events
      WHERE producer_run_id = {run_id:String}
      GROUP BY event_id LIMIT 5"' sh RUN_ID
```

### Explain

The producer's `--count` counts originals; duplicates are additional sends.
A duplicate preserves the event's identity and business values while refreshing
its send sequence and `produced_at`. Recovery can repeat the same send sequence;
[Exercise 7](#7-separate-intentional-duplicates-from-replay-duplicates) explores
that after you understand checkpoints.

## 2. Create a hot Kafka partition

### Predict

`tenant_id` is the Kafka key. Predict whether every `tenant-hot` record goes to
the same partition and how that affects per-partition offsets and lag.

### Run

```bash
docker compose --profile tools run --rm producer \
  --rate 1500 --count 100000 \
  --hot-tenant-rate 0.95 \
  --duplicate-rate 0 --late-rate 0 --bad-json-rate 0 \
  --trace-sample-rate 0.002
```

### Observe

- Producer summary logs: acknowledgement count and partition distribution.
- Kafka dashboard: message/byte rate and broker requests.
- Kafka Console: partition end offsets.
- Flink dashboard: **Kafka source offsets by partition** and **Kafka source
  backlog by subtask**. A source subtask may own multiple partitions.

### Verify

```bash
make lag
docker compose exec -e KAFKA_OPTS= kafka \
  /opt/kafka/bin/kafka-get-offsets.sh \
  --bootstrap-server kafka:19092 --topic telemetry.raw
```

### Questions

- Why does adding more consumers not split a single Kafka partition?
- Which partition key would distribute this workload more evenly?
- What ordering guarantee would that alternative key sacrifice?

<details>
<summary>Explanation</summary>

Kafka hashes a non-null key deterministically, so one tenant maps to one
partition. A partition has one active consumer within a group, which makes that
partition the unit of parallelism and ordering. A composite key such as
tenant/device would spread load but would only preserve order per device.

</details>

## 3. Follow malformed data into the DLQ

### Predict

Predict how raw-topic offsets, Flink valid/invalid counters, ClickHouse rows,
and DLQ offsets should reconcile.

### Run

```bash
docker compose --profile tools run --rm producer \
  --rate 200 --count 5000 \
  --bad-json-rate 0.10 \
  --duplicate-rate 0 --late-rate 0 --hot-tenant-rate 0
```

### Observe

- Grafana pipeline dashboard: valid, invalid, and DLQ counter rates.
- TaskManager JSON logs: sampled parse failures and bounded error categories.
- Kafka Console: `telemetry.dlq` payloads and partition offsets.

For the direct log view, run `make logs SERVICE=taskmanager`. With the optional
logs profile, use the LogQL selector from the introduction and add
`| message="invalid_record_routed_to_dlq"`.

### Verify

```bash
make dlq
docker compose exec -e KAFKA_OPTS= kafka \
  /opt/kafka/bin/kafka-get-offsets.sh \
  --bootstrap-server kafka:19092 --topic telemetry.dlq
```

### Questions

- Why retain the full payload in the DLQ but only a truncated sample in logs?
- Why should exception messages not become Prometheus labels?
- What delivery guarantee does the DLQ sink provide during recovery?

<details>
<summary>Explanation</summary>

The DLQ is replayable data; logs are diagnostic samples. Full payload logging
amplifies cost and may leak sensitive content. Error categories are bounded,
which makes them safe metric dimensions; arbitrary messages are not. The DLQ
Kafka sink is at-least-once and participates in checkpoint flushing.

</details>

## 4. See event time and watermarks diverge

### Predict

The watermark trails the greatest observed event time by ten seconds. Predict
which records will be marked late when event times are backdated by 15–300
seconds.

### Run

```bash
docker compose --profile tools run --rm producer \
  --rate 300 --count 20000 \
  --late-rate 0.40 \
  --duplicate-rate 0 --hot-tenant-rate 0 --bad-json-rate 0
```

### Observe

- Flink dashboard: **Operator watermarks**, **Input watermark lag**, and
  **Observed late records** (`lab_records_late`).
- Pipeline dashboard: **Intentional vs observed lateness**.
- Recent rows where `is_late_at_flink = 1`.

### Verify

```bash
docker compose exec -T clickhouse sh -ec '
  clickhouse-client --user "$CLICKHOUSE_USER" --password "$CLICKHOUSE_PASSWORD" \
    --query "$1"' sh "SELECT injected_late, is_late_at_flink, count(), quantiles(0.5,0.95,0.99)(lateness_ms) FROM perfmon.telemetry_events GROUP BY ALL ORDER BY ALL"
```

### Questions

- Why is “intentionally old” not always identical to “late relative to the
  current watermark”?
- What happens to a watermark when an input partition stops producing?
- What does the configured idle timeout change?

<details>
<summary>Explanation</summary>

Lateness is relative to the watermark at arrival, not wall-clock age alone. A
backdated record can arrive before the watermark advances past it. Idle-input
detection prevents a silent partition from holding the global watermark back
forever after the configured timeout.

</details>

## 5. Kill a TaskManager during checkpoints

### Predict

Predict the order in which these signals change: job state, checkpoint failure,
consumer lag, restart count, ClickHouse writes, and duplicate rows.

### Run

Start an unbounded producer:

```bash
docker compose --profile tools run --rm producer \
  --rate 1000 --count 0 \
  --duplicate-rate 0 --late-rate 0 --bad-json-rate 0
```

In another terminal:

```bash
docker compose kill taskmanager
docker compose up -d taskmanager
```

Stop the producer with Ctrl-C after recovery.

### Observe

- Flink UI: failed task attempt, restart, and checkpoint history.
- Flink dashboard: **Failed checkpoints**, **Full restarts**, and **Kafka source
  backlog by subtask**; pipeline dashboard: **Ingest throughput**.
- Kafka: group lag growing and then draining.
- ClickHouse: unique events versus stored rows.
- TaskManager recovery logs: `make logs SERVICE=taskmanager` or the introductory
  Loki selector.

### Verify

```bash
make lag
make latency
```

### Questions

- Why does recovery use Flink checkpoint state rather than the displayed Kafka
  committed offset?
- Where can duplicates enter even with exactly-once checkpoints enabled?
- Why might a producer see no error during the TaskManager outage?

<details>
<summary>Explanation</summary>

Kafka remains available, so the producer continues successfully. Flink restores
source positions and operator state from its latest successful checkpoint.
The JDBC sink cannot atomically coordinate a ClickHouse commit with a Flink
checkpoint, so rows inserted after the checkpoint snapshot can be replayed.

</details>

## 6. Turn a ClickHouse outage into backpressure

### Predict

Predict how long the JDBC sink retries before upstream operators become busy or
backpressured and Kafka pending records grow.

### Run

Keep an unbounded producer running, then execute:

```bash
docker compose stop clickhouse
```

Wait 30–60 seconds while watching Grafana and Flink, then recover:

```bash
docker compose up -d clickhouse
```

### Observe

- TaskManager logs: JDBC connection/retry failures. Run
  `make logs SERVICE=taskmanager`, or use the introductory Loki selector after
  `make up-logs`.
- Flink UI: backpressure and failed/restarted attempts.
- Kafka/Flink dashboard: pending records and consumer lag.
- ClickHouse dashboard after recovery: insert burst, parts, and merges.

### Verify

```bash
make lag
make latency
```

### Questions

- Why does pressure propagate from the sink toward the source?
- When would checkpoint timeout become the dominant failure?
- Why can recovery produce a short ClickHouse insert spike?

<details>
<summary>Explanation</summary>

The sink stops accepting records while retrying or restarting. Bounded Flink
network buffers fill, upstream operators stop emitting, and Kafka retains the
unconsumed backlog. Once ClickHouse recovers, buffered/replayed data produces a
catch-up burst.

</details>

## 7. Separate intentional duplicates from replay duplicates

### Predict

Predict how the same `event_id` can have either multiple producer sequence
numbers (separate sends) or the same sequence number repeated (sink replay).
Decide which counters and timestamps should change in each case.

### Run

In terminal 1, keep an anomaly workload running:

```bash
docker compose --profile tools run --rm producer \
  --rate 1000 --count 0 \
  --duplicate-rate 0.05 --late-rate 0 \
  --hot-tenant-rate 0.50 --bad-json-rate 0
```

After at least two checkpoints have completed (normally 20–30 seconds), run in
terminal 2:

```bash
make checkpoints
docker compose kill taskmanager
docker compose up -d taskmanager
```

Watch the job return to `RUNNING`, then stop terminal 1 with Ctrl-C after
`make lag` shows the backlog draining.

### Observe

- Flink dashboard: **Completed checkpoints**, **Failed checkpoints**, **Full
  restarts**, and **Kafka source backlog by subtask**.
- Kafka dashboard: **Consumer progress gap** while the TaskManager is absent.
- Pipeline and ClickHouse dashboards: stored/observed duplicate rows.
- TaskManager logs: recovery from checkpoint and the JDBC sink restart; use
  `make logs SERVICE=taskmanager` or the introductory Loki selector.

### Verify

```bash
docker compose exec -T clickhouse sh -ec '
  clickhouse-client --user "$CLICKHOUSE_USER" --password "$CLICKHOUSE_PASSWORD" \
    --query "$1"' sh "SELECT producer_run_id, event_id, count() AS rows, uniqExact(producer_sequence) AS sends, count() - uniqExact(producer_sequence) AS replay_copies, countIf(injected_duplicate) AS intentional_copies FROM perfmon.telemetry_events GROUP BY producer_run_id, event_id HAVING rows > 1 ORDER BY rows DESC LIMIT 20"
```

### Questions

- Which repeated rows have different producer sequence numbers?
- Which repeated rows have the same producer sequence number?
- Where would you implement deduplication, and what state-retention trade-off
  would that introduce?

<details>
<summary>Explanation</summary>

Intentional duplicates are separate producer sends and therefore have distinct
sequence numbers. A replay of an already inserted send repeats the same
sequence. Flink keyed-state deduplication gives immediate control but needs a
TTL; a ClickHouse replacing engine simplifies storage but changes query and
merge semantics.

</details>

## 8. Observe Flink `keyBy`, shuffle, and managed keyed state

This is the hands-on gate for Curriculum Session 8. The normal job keeps the
learning operator disabled. In this **Experiment**, restore the running job from
a savepoint and explicitly submit the feature-gated path with
`ENABLE_KEYBY_LAB=true`. Do not run `make reset`: the point is to preserve the
source positions while changing the job graph.

The enabled path is:

```text
Kafka source / validation subtasks
  → keyBy(tenant_id) HASH exchange
  → count-records-by-tenant subtasks
  → per-tenant managed ValueState
  → lateness observation and ClickHouse
```

### Predict

Before changing the running job, write down your answers:

- Will the Kafka source subtask that reads `tenant-hot` necessarily have the
  same index as the downstream Flink subtask that owns `tenant-hot`?
- Which graph edge should appear when `keyBy(tenant_id)` is enabled?
- With four downstream subtasks and one overwhelmingly hot key, how many
  subtasks can update that key's `ValueState`?
- Should shuffle bytes be local or remote when all four slots belong to one
  TaskManager?
- Which state is expected to restore from the old job, and which state is new?

Do not continue until you have made a prediction for all five.

### Activate via savepoint

First confirm the lab has one named running job and no separate producer:

```bash
make status
make checkpoints
```

Create a savepoint while draining and stopping that sole job:

```bash
make keyby-savepoint
```

Copy the exact `file:/...` savepoint path printed by the target. Rebuild the
Flink services only after the old job has stopped, then supply that path
explicitly:

```bash
make keyby-rebuild
make keyby-submit SAVEPOINT=file:/copy/the/exact/path/printed/above
```

`keyby-submit` is the activation boundary: it injects
`ENABLE_KEYBY_LAB=true`. Restoring preserves the Kafka source positions from
the prior job. Because `count-records-by-tenant` did not exist in that prior
job, its managed tenant counts start empty.

After learning the individual savepoint steps, these guarded shortcuts make it
easy to switch or restart the live lab:

```bash
make keyby-on     # baseline → keyBy; new keyed state starts empty
make keyby-off    # keyBy → baseline; removed keyed state is not restored
make flink-reset  # restart whichever mode is currently running
```

Each command drains the sole running job to a canonical savepoint, rebuilds
only the Flink services, and restores Kafka source positions. Repeating
`keyby-on` or `keyby-off` in the already-selected mode is a no-op.
`flink-reset` restores the current mode and all matching state; it does not
delete Kafka, ClickHouse, savepoint, or other named-volume data. It is distinct
from the destructive repository-wide `make reset` target.

### Run

Generate the bounded, valid, deliberately hot-key workload:

```bash
make produce-keyby
```

Do not run another producer at the same time. This target sends 20,000 originals
at 500 records/second with 95% `tenant-hot`, zero duplicate/late/malformed
injection, and zero delivery-trace sampling, so the subtask distribution is
about partitioning rather than data-quality branches.

### Observe

Run the bounded observation target while the workload is active or immediately
after it completes:

```bash
make observe-keyby
```

Correlate its output with these views:

- Flink UI job graph: a separate keyed downstream vertex and a `HASH` input
  edge into `count-records-by-tenant`, with parallelism four.
- Grafana Flink dashboard: **Before / after keyBy by subtask**, **Keyed load and
  tenant-hot state**, and **keyBy shuffle input: local / remote**.
- `lab_keyed_records`: records handled by each downstream keyed subtask.
- `lab_hot_tenant_state_count`: positive on only the subtask that owns
  `tenant-hot`; zero on the other subtasks. It is the hot tenant's state value,
  not the total number of state entries.
- Local shuffle input: positive while the HASH exchange moves records. Remote
  shuffle input: expected to remain zero because this lab has one TaskManager.

The Kafka source and Flink keyed subtask indexes describe different ownership
domains. Matching index numbers, if they happen, do not mean Kafka partitioning
and Flink `keyBy` are the same operation.

### Verify

Re-run the aggregate observation after Prometheus has scraped the workload, then
inspect bounded state milestones and checkpoint progress:

```bash
make observe-keyby
make verify-keyby
make keyby-logs
make checkpoints
```

`make verify-keyby` is read-only and prints `VERIFY_KEYBY=PASS` only when the
graph, four-subtask metrics, one hot-state owner, positive recent local shuffle,
and zero recent remote shuffle all agree. The evidence is complete only when
all of the following are true:

1. The plan reports a `HASH` input into the keyed vertex.
2. The keyed operator reports four subtasks, while one subtask dominates the
   workload because it owns `tenant-hot`.
3. Exactly one subtask has a positive hot-tenant state gauge.
4. `keyed_state_milestone` logs keep the same `tenant-hot` owner while its
   managed count increases.
5. Local shuffle traffic is present and remote shuffle traffic is zero.
6. A checkpoint completes after the stateful operator has processed records.

Do not use the monotonically increasing `lab_keyed_records` metric as managed
state evidence: it is an operational counter for the current task attempt.
`tenant-record-count` is the checkpointed `ValueState`.

### Explain

Answer these before marking Session 8 complete:

- Why can the before-`keyBy` and after-`keyBy` subtask distributions differ?
- Why does the HASH edge break the original operator chain?
- Why can only one subtask read or update `tenant-hot` state at a time?
- Why does adding parallelism not split one hot key across more subtasks?
- What design change could split that load, and which ordering/aggregation
  guarantees would become more complicated?
- Why is a production state-retention policy a correctness decision rather than
  only a storage optimization?

<details>
<summary>Explanation</summary>

Kafka first assigns records to topic partitions using the producer's key. Flink
source subtasks own those Kafka partitions. `keyBy(tenant_id)` then applies
Flink's key-group assignment and sends each tenant across a HASH edge to one
downstream keyed subtask. The two ownership calculations are independent, so a
record can move to a different subtask even though the business key is the
same.

Every record for one key must reach one active keyed subtask so Flink can give
that key ordered, exclusive access to its state. Increasing parallelism creates
more possible owners but cannot divide `tenant-hot` itself. Key salting or a
composite key can spread a hot tenant, but then a second aggregation stage is
needed and strict tenant-wide ordering is lost or must be rebuilt.

The current lab intentionally has no State TTL. Its synthetic tenant set is
small, but an unbounded production keyspace would retain state and enlarge
checkpoints indefinitely. A production TTL must follow the required replay,
deduplication, or aggregation horizon. Expiry can make an old key look new and
reset its count, so TTL cleanup semantics must be designed, tested, and
monitored rather than chosen only to save disk.

Because all subtasks run in one TaskManager, the HASH exchange uses local
shuffle channels. Remote shuffle requires sender and receiver subtasks on
different TaskManagers; a zero remote rate here is expected topology evidence,
not proof that no shuffle occurred.

In production, this pattern exposes a classic hot-key incident: one keyed
subtask becomes busy/backpressured while its peers remain underused. Scaling the
operator alone does not fix it; the key model or aggregation design must change.

</details>
